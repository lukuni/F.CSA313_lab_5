## Даалгавар 1 — Анхны хүсэлт ба oracle

- `PUT {{baseUrl}}/students/B231234567` → `{"status":"active","coursesTaken":["CS201"]}`
- `PUT {{baseUrl}}/courses/CS313` → `{"prerequisites":["CS201"]}`
- `POST {{baseUrl}}/registrations` → `{"studentID":"B231234567","courseID":"CS313"}`
- Oracle 1: статус код **201**; Oracle 2: `result` = **"OK"**
- `baseUrl` = `http://localhost:3000` (collection variable)

Энэ нь collection-ийн **T01** тест болсон.

## Даалгавар 2 — Тест дизайн

### Алхам 1. Бие даан тестлэгдэх функц

`POST /registrations` — оюутныг хичээлд бүртгэх. Оролт: `studentID`, `courseID`. Гаралт: статус код ба `result`.

`server.js`-ийн шалгах дараалал: талбар дутуу → оюутан байхгүй → идэвхгүй → хичээл байхгүй → урьдач нөхцөл → OK. Давхар алдааны үед **эхэнд шалгагдсан** алдаа буцна.

### Алхам 2–3. Сонголтууд ба төлөөлөх утгууд

| № | Сонголт (parameter / environment) | Анги (choice) | Төлөөлөх утга |
|---|---|---|---|
| C1 | studentID-гийн хүчинтэй байдал | идэвхтэй | `B231234567`, `status:"active"` |
| | | идэвхгүй | `B230000003`, `status:"inactive"` |
| | | байхгүй | `B000000000` (PUT хийгдээгүй) |
| C2 | Оюутны үзсэн хичээлүүд (`coursesTaken`) | урьдачийг хангана | `["CS201"]` (CS313-д) |
| | | урьдачийг хангахгүй | `[]` эсвэл `["CS201"]` (CS401-д) |
| C3 | courseID-гийн хүчинтэй байдал | байгаа | `CS313`, `CS401`, `CS101` |
| | | байхгүй | `CS999` (PUT хийгдээгүй) |
| C4 | Хичээлийн урьдач нөхцөл | бүгдийг үзсэн | CS313 ← `["CS201"]`, оюутан `["CS201"]` |
| | | огт үзээгүй | CS313 ← `["CS201"]`, оюутан `[]` |

**Боломжгүй / хүрэх боломжгүй хослолууд:**
- Оюутан **байхгүй** × `coursesTaken` (хангана/хангахгүй) — байхгүй оюутанд үзсэн хичээл гэж байхгүй.
- Хичээл **байхгүй** × урьдач нөхцөл (бүгд/огт/зарим) — байхгүй хичээлд урьдач нөхцөл байхгүй.
- Оюутан **идэвхгүй** × урьдач нөхцөл — сервер идэвхгүй гэдгийг эхэлж шалгадаг тул урьдачийн шалгалтад хэзээ ч хүрэхгүй (T07-оор баталсан).

## Даалгавар 4 — Newman

| Ажиллуулалт | Команд | assertions executed / failed | Exit code |
|---|---|---|---|
| PASS | `newman run lab05-collection.json` | 26 / 0 | **0** |
| FAIL | `newman run lab05-collection-fail.json` | 26 / 1 | **1** |
| DOWN (сервер унтарсан) | `newman run lab05-collection.json` | 26 / 26 (requests failed 26, ECONNREFUSED) | **1** |

- **CI quality gate:** Newman тест унавал exit code 1 буцаадаг тул CI pipeline (ж: GitHub Actions) энэ алхамд зогсож, алдаатай код merge/deploy хийгдэхээс сэргийлнэ; exit code 0 бол gate нээгдэнэ.
- **DOWN = интерфейсийн алдаа:** DOWN үед сервер хариу огт өгөөгүй (`ECONNREFUSED` — холболт тогтоогдоогүй) тул энэ нь системийн буруу зан төлөв биш интерфейсийн/орчны алдаа, харин FAIL-д сервер зөв 201 хариулсан ч бидний oracle буруу (200) байсан тул oracle-ийн алдаа юм.

## Дүгнэлт

Тест дизайны 5 алхмаас хамгийн их бодол шаардсан нь сонголтуудыг тодорхойлж, эквивалент ангид хуваах (2–3-р алхам) байсан. Учир нь `server.js` алдааг тодорхой дарааллаар (талбар → оюутан → идэвхтэй эсэх → хичээл → урьдач нөхцөл) шалгадаг тул давхар алдааны үед ямар `result` буцахыг кодыг уншиж байж л зөв таамаглах боломжтой байсан. Боломжгүй хослол хэд хэд таарсан: байхгүй оюутанд үзсэн хичээл гэж байхгүй, байхгүй хичээлд урьдач нөхцөл гэж байхгүй тул эдгээр хослолыг тест болгох утгагүй. Мөн идэвхгүй оюутны хувьд урьдач нөхцөлийн шалгалтад хэзээ ч хүрдэггүйг T07 тест баталсан — энэ нь бодит утгаараа хүрэх боломжгүй салбар юм. Тест бүрийг өөр оюутны ID-тай, өөрийн setup-тай болгосноор тестүүд бие даасан болж, дарааллаас үл хамааран давтан ажиллуулахад тогтвортой PASS гарсан. Сервер in-memory тул `registrationID` ажиллуулах бүрд өсдөгийг Postman дээр ажиглаж (эхний удаа 1 биш 2 гарсан), яг утгын оронд зөвхөн тоо эсэхийг шалгах нь зөв oracle гэдгийг ойлгосон. Тестүүд нэг боломжит согог илрүүлсэн: T01-ийг олон удаа ажиллуулахад ижил оюутан ижил хичээлд дахин дахин 201 OK авч бүртгэгддэг, өөрөөр хэлбэл давхар бүртгэлийг сервер шалгадаггүй. Үүнээс гадна `status: ""` илгээхэд `||` оператороос болж оюутан идэвхтэй болж, `"Active"` (том үсэгтэй) бол идэвхгүй гэж тооцогддог нь оролтын шалгалт сул байгааг харуулж байна. FAIL болон DOWN ажиллуулалтыг харьцуулснаар oracle-ийн алдаа (сервер 201 зөв хариулсан ч бид 200 хүлээсэн) ба интерфейсийн алдаа (ECONNREFUSED — холболт огт үгүй) хоёрын ялгааг тодорхой ойлгосон. Newman-ы exit code нь CI quality gate болж ажилладаг тул эдгээр тестийг pipeline-д оруулбал алдаатай өөрчлөлт автоматаар зогсоно.

## Нэмэлт даалгавар (AI өнцөг)

`server.js`-ийн кодыг өгөөд *"Энэ API-гийн POST /registrations функцийн сонголтуудыг тодорхойлж, сонголт бүрийг эквивалент ангид хуваагаад, ангиудын хослолоор Postman тестүүд үүсгэ"* гэж AI туслахаас (Claude) хүссэн. AI 8 сонголт, 25 тест кейстэй Postman collection гаргасан бөгөөд үүнийг өөрийн серверт Newman-аар ажиллуулж (101 assertion, 4 failed), өөрийн дизайнтай (5 сонголт, 11 спецификаци, 26 assertion) харьцуулав.

**(1) AI ямар сонголт, ангийг мартсан бэ?:** AI ямар нэг сонголтыг мартаагүй ч 3 тестийн нэрэнд (`"missing = ["P2"]"`) давхар хашилтыг escape хийлгүй бичсэнээс `SyntaxError` гарч, `ERROR_PREREQUISITES`-ийн oracle-ууд огт ажиллаагүй. Өөрөөр хэлбэл хамгийн чухал алдааны ангийн нэг нь "шалгагдсан" мэт харагдавч бодит байдалд шалгагдаагүй үлдсэн.

**(2) Миний мартсаныг AI олсон уу?:** Тийм — AI falsy утга (`""`, `null`), тоон ID, хоосон body, `"Active"` том үсэгтэй status зэрэг миний анхаараагүй ангиудыг нэмсэн. Хамгийн чухал нь `Object.prototype`-ийн нэртэй ID байсан: studentID = `"toString"` бол сервер `ERROR_NO_STUDENT` биш `ERROR_INACTIVE_STUDENT` буцаадаг, courseID = `"constructor"` бол `course.prerequisites.filter` дээр `TypeError` шидэж сервер бүхэлдээ унадаг — энэ хоёр нь `students`/`courses`-ийг энгийн `{}` объектоор хадгалснаас үүдэлтэй бодит согог юм.

**(3) AI-ийн oracle-ууд зөв байсан уу?:** `SyntaxError`-той 3 тестээс бусад oracle-ууд (статус, `result`, registrationID-ийн яг утгыг шалгаагүй) зөв байсан бөгөөд бүтэлгүйтсэн 4 assertion бүгд дээрх 2 согогоос үүдэлтэй. Ерөнхийдөө AI эквивалент ангийг илүү өргөн хүрээнд санал болгодог ч бичсэн тестийг нь заавал ажиллуулж шалгах шаардлагатай гэдгийг энэ дасгал харуулав.
